[01] // PROBLÈME

Un build, c'est pour quoi faire ?

Dans Destiny 2, un build combine une sous-classe, trois armes, des statistiques d'armure, des perks et des fragments. Les joueurs partagent des milliers de builds sans dire à quoi ils servent. L'objectif : classer automatiquement un build en pve_add_clear, pve_dps, pve_survival, pvp_aggressive, pvp_defensive ou support, et exposer la prédiction dans Destiny Hub, la plateforme React du projet.

40 variables par build : type de classe, sous-classe, types d'armes cinétique / énergétique / lourde, exotiques, nombre de perks offensifs et défensifs, six statistiques totales, résistances, type d'activité, super, saut, grenade, mêlée, aspects et fragments.

[02] // DONNÉES

ETL sur l'API Bungie, puis des builds réels

  • Collecte : scripts Python sur l'API Bungie.net (manifest des objets, activités, perks), synchronisation planifiée, stockage Supabase.
  • Première version : 3 000 builds synthétiques générés à partir des règles du jeu pour amorcer le modèle.
  • Deuxième version : scraping de builds publics avec Playwright (Mobalytics, Cloudflare en prime), étiquetage semi-automatique puis 52 corrections manuelles. 392 builds réels au final.
  • Analyse : cinq notebooks (méta, contexte, corrélations, archétypes, robustesse) avant le moindre entraînement.

[03] // LA FUITE

Accuracy 1.00 : trop beau pour être vrai

Premier entraînement sur les données synthétiques : régression logistique, Random Forest et XGBoost à 1.00 d'accuracy. Un score parfait sur six classes est un symptôme, pas un résultat.

Cause : quatre colonnes score_dps, score_survival, score_mobility, score_synergy étaient calculées à partir de l'étiquette. Le modèle lisait la réponse dans les features.

Correctif : les quatre scores sont exclus, 20 % des étiquettes sont volontairement bruitées et chaque statistique reçoit un bruit de ± 10 points pour simuler des builds ambigus. Le Random Forest retombe à 0.81 de F1. C'est le chiffre honnête, et le pipeline _run_honest_metrics.py le reproduit à chaque exécution.

[06] // MISE EN PROD

Une API, une CI qui refuse les mauvais modèles

  • API : FastAPI, POST /predict renvoie la classe et la confiance, documentation Swagger. Si l'API est arrêtée, Destiny Hub affiche « Analyse ML indisponible » sans casser la page.
  • CI : GitHub Actions réentraîne le modèle à chaque push puis lance pytest : artefacts présents, 6 classes, forme des prédictions, et F1 sous le seuil = modèle rejeté.
  • Monitoring : chaque prédiction est journalisée (predictions_log.jsonl) avec un champ true_label rempli plus tard par le retour utilisateur. Un script calcule la dérive et lève des alertes.
  • Réentraînement : retrain.py à partir du journal corrigé.

[07] // CE QUE JE REFERAIS

Plus de données avant plus de modèle

  • Collecter 100 builds pvp_aggressive de plus avant de toucher aux hyperparamètres : la classe est trop rare pour conclure.
  • Calibrer les probabilités (Platt ou isotonique) : la confiance affichée dans Destiny Hub doit vouloir dire quelque chose.
  • Garder le réflexe : un score parfait se vérifie avant d'être montré.
